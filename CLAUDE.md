# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Ball Wars is a Flutter app (web first, also iOS/Android) that simulates "ball battles": 2–4 custom balls bounce around inside a circular arena, each one projecting a fan of lines to the rim. Opponents cut those lines, and a ball is out once all its lines are cut. Rendering is plain Dart plus `CustomPainter`; the spec explicitly says **not** to use the Flame engine. Runtime dependencies beyond the SDK: `audioplayers`, `file_picker`, `flutter_svg`, `http`, `path_provider`, `supabase_flutter`. Fonts (Manrope variable, JetBrains Mono Medium) are bundled in `assets/fonts` with their OFL licenses. Manrope is a variable font, so set its weight with `FontVariation('wght', …)` through `AppText.ui`, not `FontWeight` alone. Images are handled as raw `Uint8List` bytes, never `dart:io` `File`, so they work on web.

Design docs (read them before larger changes):
- `docs/CLAUDE_CODE_BALL_WARS_SPEC.md`: the original full spec (directory layout, UI, theme).
- `docs/superpowers/specs/2026-09-21-ball-wars-mobile-sharing-design.md`: mobile/responsive layout, the **determinism** requirement, and the planned sharing/gallery feature.
- `docs/superpowers/plans/2026-09-21-ball-wars-core-simulator.md`: the implementation plan.
- `docs/psuedocode.txt`: reference pseudocode for the thread/line-cutting game loop that the current mechanics follow.

- `docs/reference_video_analysis.md`: frame-by-frame findings from that video (core mechanic, physics gaps, effects still to build).

```bash
flutter pub get
flutter run -d chrome                 # primary target
flutter analyze                       # lints: package:flutter_lints/flutter.yaml
flutter test                          # all tests
flutter test test/features/arena_simulation/application/match_simulation_controller_test.dart
flutter test --plain-name "determinism"   # tests whose name contains this text

#   add --dart-define=KEEP_VIDEO=true to save the result to the phone's Movies/BallWars
```

Android releases: pushing a tag `v*` runs `.github/workflows/release-apk.yml`. It builds an APK signed with the release key from the `ANDROID_KEYSTORE_BASE64` / `ANDROID_KEYSTORE_PASSWORD` / `ANDROID_KEY_ALIAS` / `ANDROID_KEY_PASSWORD` repository secrets, and attaches it to a GitHub Release. Locally the key lives in `android/upload-keystore.jks` plus `android/key.properties` (both git-ignored; without them release builds fall back to the debug key). Never change or lose that key, or installed copies can't be updated.

Deployment: `.github/workflows/deploy-pages.yml` runs the tests, builds web with `--base-href /<repo>/` and publishes to GitHub Pages on every push to `master`. Under Git Bash, building locally with a base href needs `MSYS_NO_PATHCONV=1`, otherwise `/ballwars/` gets rewritten into a Windows path.

UI text never uses en or em dashes; use a plain `-` (user rule).

## Architecture

The code is organized by feature under `lib/features/<feature>/{domain,data,application,presentation}`, with shared theme, widgets and utils in `lib/core/`. `test/` mirrors `lib/`. There is no state-management package: screens own their controllers and call `setState`. `BallWarsApp` (`app.dart`) takes the Supabase-backed repositories (custom groups, settings, admin auth, short links) through its constructor; all of them are optional, so tests run without a backend. Navigation goes Home → `MatchSetupScreen` / `MyGroupsScreen` / `SettingsScreen`, and `MatchSetupScreen` → `ArenaBattleScreen(config: MatchConfig)`. The Ball Library and the "My Balls" category are gone. `LocalBallRepository.presets` stays only so that old replay links with `p.<presetId>` still resolve.

### Offline play, icon and splash

On start (`BallWarsApp(syncOffline: true)`, set in `main.dart`), a loading screen waits only for the settings and the pack catalog. Then `OfflineSync` (`core/offline`) runs in the background, and Home shows a "Saving balls for offline… n/total" line until it's done. That class downloads every ball image Match Setup can show into `OfflineStore`: files in the app support folder on Android, Cache Storage via `web/offline_store.js` on web. Only missing images download. Pack image URLs carry `?v=<content hash>` from `packs.json`, which `tool/build_packs.mjs` writes, so a changed image downloads again. `BallImageLoader` reads the store first. The pack catalog, groups (`groups:mine:<uid>` / `groups:saved:<uid>` / `groups:all`, per account) and settings keep their last good copy in the store and fall back to it offline. Startup queries use `.retry(enabled: false)`; otherwise postgrest's backoff makes an offline start take many seconds. On web the app shell itself comes from Flutter's service worker. Tests keep the default in-memory store.

The logo is `BallWarsLogoPainter` (`core/widgets/ball_wars_logo.dart`). `flutter test tool/brand/render_brand_test.dart` renders it into `assets/brand/*.png`, then `dart run flutter_launcher_icons && dart run flutter_native_splash:create` regenerates the Android, iOS and web icons and splash screens (config in `pubspec.yaml`). The loading screen draws the logo at the native splash's size, so one screen hands off to the next without a jump.

### Sound and device preferences

`GameAudio` (`core/audio`, audioplayers) plays the 8-bit sounds in `assets/sounds/`; `python tool/sounds/make_sounds.py` regenerates them (original synthesis, numpy). The five background tracks are composed in `tool/sounds/music.py`. Their ids must match `MusicTrack.all`. The admin picks one for everyone (`app_settings.music`, migration 005, Settings → MATCH MUSIC with a preview button per track); the app applies it with `GameAudio.instance.track`. **Home music** plays everywhere outside matches. It has five slow tracks, `menu_*.wav` (16 kHz, `MusicTrack.menu`), picked by the admin (`app_settings.menu_music`, migration 009, Settings → HOME MUSIC), and its own device switch on Home (`pref:menu-music`). The battle screen calls `stopMenuMusic()` / `startMenuMusic()`. Browsers block sound until the first tap, so `GameAudio.click()` starts it then. `GameAudio` itself observes the app lifecycle and pauses all music in the background. Sounds are WAV because MP3 can't loop without a gap. Every player is created with `positionUpdater = null` (`GameAudio._newPlayer`): audioplayers' default polls the position each frame while a player plays, and low-latency effect players never report completion, which kept Android redrawing at 120 Hz with a platform call per frame. The battle screen plays a bounce or hit sound when the controller's `wallHits` / `ballHits` counters go up. Rapid repeats are thinned out, and the counters draw nothing from the RNG. In slow motion the slowed `*_slow.wav` variants play and the music slows down and gets quieter. `GameAudio.enabled` is false unless `main` sets it, so tests never touch the audio plugin. Music and sound effects each have their own toggle in Match Setup. Those toggles, rounds, speed, effects and "Don't ask again" are remembered per device in `OfflineStore` under `pref:*` keys (`DevicePrefs`, `EffectsPrefs`). Tests that depend on them reset `OfflineStore.instance` in `setUp`. If a local web build is missing a newly added plugin (MissingPluginException), run `flutter clean`; the cached plugin registrant can be stale.

### Theme and admin settings (settings)

`AppSettings` holds `headline` (default "WHO WINS?"), `themeId`, `watermarkEnabled` and `watermarkText`. It is one row in the Supabase `app_settings` table: everyone can read it, and only the admin can write it. `AppSettingsScope` (an `InheritedNotifier`) hands the settings and repositories down the tree. The theme comes from `AppPalettes` (`core/theme/app_theme.dart`): "midnight" plus the palettes from `docs/color-palettes`, each in both directions. `BallWarsColors` (a `ThemeExtension`, read with `BallWarsColors.of(context)`) mixes surfaces and the muted text color from a preset's two colors. The arena, the replay video (`ReplayStyle`) and `MatchColors` (which darkens line colors on light arenas) all follow the theme's background. The admin is a Supabase email/password user listed in the `admins` table, and `is_admin()` gates the RLS policies. The admin signs in on a **separate** `SupabaseClient` (`SupabaseAdminAuth.client`, session kept in `DevicePrefs`), so the main client keeps this device's anonymous account and its groups. Admin writes (settings, editing anyone's groups via `adminGroups` / `MyGroupsScreen.editRepository`) use that client; "In my categories" switches use the device's own. Admin Settings also has "Clean up unused images" (migration 007). `SettingsScreen` shows the admin sign-in, plus the headline, theme, watermark and "Everyone's groups" (`MyGroupsScreen(allGroups: true)`) sections.

### Simulation loop (arena_simulation)

- `ArenaBattleScreen` owns a `Ticker`. On each frame it calls `MatchSimulationController.tick(realDt * speedMultiplier)` and reads `controller.state`. It doesn't call `setState` per frame: it bumps a `_frame` notifier. `ArenaPainter` repaints from it (`repaint:`, inside a `RepaintBoundary`), and only the live readouts (scoreboard, timer, VS header, slow-motion badge) rebuild through `ListenableBuilder`s. Repaints happen only when the simulation stepped, or while effects are animating (at most about 60 fps), which matters on 120–144 Hz phones. On lock or background the music pauses, and on return the next frame's time jump is skipped. The screen also handles UI-only end-game behavior: the loser dissolve animation and `WinnerModal`. Slow motion is decided by the controller (`MatchStatus.slowMotion`), and the screen only shows the badge. When a match restarts, `_skipNextDelta` resets the timing so the next frame doesn't compute a huge dt.
- `MatchSimulationController` holds all match logic. It uses a **fixed timestep** (1/60 s, accumulator, at most 10 steps per frame). Each step runs in this order: free the slots of lines deactivated from outside → integrate positions and wall bounce (`ArenaPhysicsEngine`, where wall hits claim slots) → ball-ball collisions (elastic directions, only `collisionSpeedTransfer` of the speed exchange) → move line endpoints to their owners → cut lines → elimination (with a tie-break so a match always has a winner) → win check / slow-motion status. The processing order of the balls rotates every step. Each match also rotates the layout and draws start distance, speed and tilt per ball, all to keep every contestant's odds equal. Check any change against a win-rate-by-start-position probe over many seeds; the numbers are in `docs/reference_video_analysis.md`.
- **Playback speed-up:** `MatchSimulationController.playbackSpeedUp` makes playback 0.25x faster per full minute of game time (up to 2x, not in slow motion), so long matches don't drag. It only scales the accumulator, so steps, outcome and replays are unchanged; the timer shows it (`x1.25`).
- **Unstuck button** (bottom left of the arena, in line with the sound buttons): `MatchSimulationController.requestNudge()` pushes every ball in play in a random direction at the next step, at `nudgeForce` 1 (the skill knockback scale: an arena radius per second). Directions come from the seeded RNG inside the step; the step is recorded (`nudgeSteps`), carried in replay links (`nudge=`), repeated by Replay and the video export, and the slow-motion look-ahead plans again with it (`_predict`).
- **Endless battles and End battle:** in an endless Arsenal battle (`endlessBattle`, not Mayhem) a knocked-out ball respawns (`_respawn`), its attacker gets a KO (`eliminations`) and the ball a death (`deaths`); there is no last-ball win and no look-ahead. Mayhem ends on its timer (`_finishMayhem`). Endless (non-Mayhem) battles also show an **End battle** button right of Unstuck (`arena-end-battle`; it reads "Ending after next KO" and is disabled once pressed; where the row is too narrow, as on phones, it is icon-only with the label in its tooltip; in a replay it is disabled and shows the ending label only from the recorded step). `requestEndAfterKnockout()` is applied at the next step boundary and recorded as `endStep`; the first knockout from then on doesn't respawn and finishes the match: `winnerId` is the tally leader among the balls still standing (KOs, then fewer deaths, then life, `_tallyRanking`, same as Mayhem; if nobody is standing, everyone but the defeated ball), `lastEliminatedId` is the defeated ball and `winningMove` the move that defeated it, so the usual dissolve, finisher and WinnerModal tally follow. No RNG draws are added. The step travels like nudges: ctor `endAfterKnockoutStep`, replay links `end=` (1..216000, one hour of game time like `nudge=`, `ReplayLink.maxLinkStep`; only with `endless=1` and not Mayhem), `ArenaBattleScreen(endStep:)`, Replay and the video export.
- **Replay vs Play again:** the winner card's Replay re-runs the finished match with its seed (not counted again); Play again (and the in-match New match) starts new seeds, even for a match opened from a link. While a round is a replay (after Replay, or a match opened from a link or the saved replays list, in its first round) the winner card has no Save replay button (`_watchingReplay`); Share link and Save video stay. Play again, New match and the next round of a series bring it back. Changing the category in Match Setup clears the picks.
- **Slow motion uses a look-ahead.** Slow motion only scales playback time, never the step sequence. So the controller's constructor plays the same match once off-screen (`lookAhead`, about 30–40 ms on desktop) to learn the finishing step and the step from which the endgame is final. The admin setting (`app_settings.slow_motion_lines` / `slow_motion_before_win`, migration 006) either starts slow motion once a ball is down to N lines for good (a ball that will recover never triggers it), or N seconds of game time before the winning cut. Code or tests that change a match by hand mid-game can't be foreseen, so they should pass `lookAhead: false`.
- **Ball size** (`BallSize` in `match_config.dart`: Smallest 0.6×, Small 0.8×, Medium 1.0×, Large 1.25×) scales `ballRadiusRatio` through the controller's `ballScale`. Every ball shares it, and a 300-seed probe showed no start-position bias and similar match lengths at every size. It changes the match, so it travels in replay links (`size=xs|s|l`, left out for medium), short links (`replays.size`, migration 008) and the video export.
- **Match modes and power-ups** (spec `docs/superpowers/specs/2026-10-23-power-ups-design.md`).
  - **Modes:** `MatchConfig.mode` is one of:
    - **Threads:** the default, and identical to before. A test pins 40 recorded results; no power-up code runs and no extra RNG draws happen.
    - **Arsenal:** no threads; `SimulationBall.life` runs 100 to 0, and plain bumps deal 5 base damage to both balls. Crowded matches multiply damage by `(count / 2)^2`.
    - **All-Out:** threads are the life, and power-up hits cut threads.
  - **`PowerUpSystem`** (`application/power_up_system.dart`) is created only in Arsenal and All-Out. The controller calls `step()` right after the ball-ball collisions. It handles:
    - spawning: first at 1 s, then every 5 s for 2 balls (`PowerUpTuning.spawnInterval`: faster with more balls), at most balls + 1 on the field (`maxOnField`), the oldest removed; each spawn picks the emptiest quadrant, away from the rim; field power-ups are 0.7x the ball radius;
    - arena items have three categories: weapons, power-ups and traps. A ball equips one weapon at a time unless dual wield is enabled; power-ups apply without removing equipment; traps are always enabled, spawn only near the arena boundary, preserve equipment and do not increment the pickup counter;
    - guns: a 1 s aim, then projectiles;
    - contact effects: knife, shield and bash; the shield aims (`shieldAngle`) but blocks from every side;
    - melee reach: `SkillDefinition.meleeReach` (0..3 ball radii, default 0, JSON `melee_reach` written only when above 0; editor "Melee reach" in Damage & Timing) lets a contact weapon (blade, orbiting flail, shield bash, collision-trigger skill) strike without a bump. `PowerUpSystem._strikeWithMeleeReach` runs once per step right after the orbiting flail: every strike (nearest alive non-ghost opponent within `r1 + r2 + reach * r1`) is chosen from the balls as they stood before any lands, then all are applied through `_melee` with the targets' held weapons from before, so mutual reach hits both sides whatever the ball order (used up as on a bump, a shield still bashes only an unarmed ball). No RNG draws, and with reach 0 matches are unchanged (`melee_reach_test.dart` pins recorded results);
    - apple (Arsenal: past full life up to 150, shown as gold hearts), speed, freeze, magnet and ghost; a ghost passes through balls and is immune;
    - mines (`PowerUpKind.mine`, `ArmedMine`): the first ball to touch one arms it where it lies (keeping what it holds), an opponent touching it sets it off at once, and its owner is never hurt by it;
    - grenades are held like guns: aimed for 1 s, then thrown at where the target was (`Projectile.landAt`); they fly over threads and blow up on a ball or where they land, sparing the thrower. Mines and grenades share `_explode`;
    - the sword is a blade like the knife (`PowerUpKind.isBlade`) with double its damage;
    - Shadow Clone (`PowerUpKind.shadowClone`, Special tier, instant like Raging Demon): yells "KAGE BUNSHIN NO JUTSU!", freezes time for the whole sequence (`_freezeTime`) and adds a `ShadowCloneAttack` (`PowerUpSystem.shadowCloneAttacks`). `shadowCloneCount` clones (default 3, 1-6) appear around the owner over 12 steps, then each in turn dashes to the nearest alive opponent and hits once through `_hit` (one every 14 steps; `dmg.shadowClone` 5 / `lines.shadowClone` 2, not scaled for crowds), and they smoke out 12 steps after the last hit. A dead target makes the next clone retarget; with no opponent left the rest vanish. The owner stays put, and clone positions are pure functions of age (no RNG). `PowerUpPainter.paintShadowClones` draws them after the balls as darkened translucent copies of the owner's body through `ArenaPainter._paintBody` (picture or face), with smoke puffs. Its icon is pixel art (`PowerUpSprites.pixelArtOnly`);
    - **combining skills (any combination):** every skill can look like another weapon (`SkillDefinition.artworkKind`, `displayKind`; only the picture changes, `baseKind` keeps the rules) and fire another projectile skill as its shots (`payloadSkillId`, a stable `builtin.<kind>` / `custom.<slug>` id). The firing skill keeps trigger, aim, cooldown, callout and the number and spread of shots; each shot carries the fired skill's definition (`_composedProjectiles`: damage, flight, return, explosion, knockback, size, tint, sound) and credits the firing skill as the move (`_composedIssuers`, finisher). `SkillLibrary.resolvePayload` follows chains (A fires B fires C: A shoots C) and turns built-in projectile weapons into projectile definitions; `payloadProblem` reports self, missing, non-projectile, loop and non-aimed references (Skill editor > Identity > Combine shows it and blocks Save; at runtime a broken reference fires the skill's own projectile). Tests: `test/features/skills/skill_composition_test.dart`;
    - the hook is aimed like a gun and thrown on a chain; a hit reels the target in (`HookPull`, yell "COME OVER HERE!"), then the owner uppercuts it (a hook hit through `_hit`) and throws it in a seeded random direction at its old speed with a short speed burst; a shield blocks it, a ghost can't be hooked;
    - feedback: balls yell what they do and hits show the damage taken (floating labels; a volley adds up in one label);
    - All-Out specials: blast thread-clearing, sword sweep (1.8x reach for 60 steps), thread snap.
  - **Global skill settings** (Skill Management > Built-in > Global, saved with the library): callout duration and screen shake each have a global value and "Let each skill set its own" (`SkillLibrary.calloutSeconds` / `skillsSetCallout`, `screenShake` / `skillsSetScreenShake`; read through `calloutSecondsFor` / `screenShakeFor`). Off: every skill uses the global value and the per-skill field is disabled (not hidden) in the editor. Defaults keep each skill's own values. The admin's Default effect visuals (Sprite or Vector for projectiles, explosions and freeze; `app_settings.*_render_mode`) also lives in this Global tab (it moved from Settings) and comes back in `SkillManagementResult.effectVisuals`. Sprite explosions and ice impacts use the real frames of `effects-animated-v3.png`, with each frame's rectangle listed in its atlas manifest (`assets/sprites/effects-animated.atlas.json`); the Vector look is drawn separately in `PowerUpPainter`.
  - **Hits:** every hit goes through `_hit`, which handles shield and ghost.
  - **Tuning:** the defaults live in `PowerUpTuning` (`domain/power_up.dart`), and tests assert through them. The admin can change most of them in Settings → POWER-UPS (`PowerUpTuningScreen`, Restore defaults). They are a `PowerUpConfig` (`domain/power_up_config.dart`: `fields` with id, group, default, range and unit; only changed values are stored), saved in `app_settings.power_ups` (migration 011). A match reads them from `MatchSimulationController.tuning` (`MatchConfig.tuning`, taken from the admin's settings at Start). They are part of the match: links carry the changed values as `t=<base64url json>` (`PowerUpConfig.encode` / strict `decode`), short links in `replays.tuning`, so replays always play with the numbers they were played with. `flutter test tool/bench/power_up_probe_test.dart` reports fairness and match length; the results are in `docs/reference_video_analysis.md`.
  - **Slow motion:** Arsenal uses "before the win", with 1.5 s when the admin chose the lines option.
  - **Weapon selection:** Match Setup's "Weapons" dialog picks which power-ups can spawn (`MatchConfig.powerUps`, null = all; at least one stays on; `pref:power-ups-<profile>`). Active custom skills are listed in the same dialog under "Your custom skills" (in the tab of their category) and are switched on their own, independently of their base weapon (`MatchConfig.customSkills` / `MatchSimulationController.customSkillIds`, null = all; per match type, stored as the ones switched off in `pref:custom-skills-off-<profile>` so new skills start on; links carry `cs=`). With everything on, the draws are unchanged. Audio switches live on the arena screen, not in Match Setup.
  - **Tiers (rarity):** built-in tiers are `tier.<kind>` in the tuning; a custom skill has its own (`SkillDefinition.rarity`, JSON `rarity`, custom skills only; null = follow the base kind's current tier, as old skills do until edited). Read a skill's tier only through `SkillLibrary.rarityOf(skill, tuning)` (null for traps) and set a custom one with `SkillLibrary.withOwnRarity` (its callout style moves with the tier when it matched the old one). The skill editor, the Skill Management list, the Weapons dialog cards (label and color via `PowerUpName(label:, rarity:)`), the field pickup ring and the "Item rarities (Legacy)" screen (`PowerUpRarityScreen(skills:)` lists custom skills and returns `PowerUpRarityResult`: built-ins to the tuning, custom tiers to the skill library) all use it, so editing a custom skill's tier never touches its built-in and the other way round. Spawning: while every spawnable custom skill sits at its base kind's tier (`PowerUpSpawnSelector.customTiersDiffer` false), `_spawn` draws exactly as before (kind by tier, then a uniform pick among the built-in and its variants); otherwise `PowerUpSpawnSelector.chooseSkill` makes each variant at another tier an entry of its own in that tier. The tier travels in the replay skill snapshot (`skills=`).
  - **Links:** the mode travels as a leading ball-list token (`m.arsenal` / `m.allout`), followed by `w.<base36 bitmask of PowerUpKind.index>` when only some power-ups are chosen. Old apps reject unknown tokens, so they refuse such links instead of misplaying them. Every Arsenal/All-Out link also carries `kc=<number of PowerUpKinds>` (strict, 1..current count): it pins the kind pool, so kinds added later never spawn when an old link plays back. A link without `kc` predates it and counts as `ReplayLink.legacyKindCount` (48, before Shadow Clone); `fromUri` then turns `powerUps` into the explicit set of the first `kc` kinds (with `kc` equal to the current count nothing changes, so no RNG draw changes). `PowerUpConfig.decode` accepts a `_tiers` list shorter than the current kinds (missing kinds keep their default tier) and rejects longer or empty ones. When adding a kind, append it last and never change `legacyKindCount`.
  - **Drawing:** `PowerUpPainter` draws the pulsing field power-ups, armed bombs, bullets (one `drawRawPoints` batch), blasts, knife slashes, and each ball's held weapon or shield on the ball. All sprites (icons, effects, projectiles, animations) come from sheet PNGs in `assets/sprites/`, each with a JSON atlas manifest (`<sheet>.atlas.json`: frame rectangles, output size, fit, padding, shared band, steps per frame, bleed notes) listed in `assets/sprites/atlas-index.json`. `SpriteRegistry` (`core/sprites`) decodes each sheet once at start, cuts every frame into its own small image and answers `SpriteRegistry.frame(id, frame)`. Ids are `powerup.<kind>`, `effect.<name>`, `projectile.<name>` and `anim.<name>`; painters get them from `PowerUpSprites` (`iconId`, `effectId`, `projectileId`, `animId`, built once so painting never formats strings) or `ArenaEffectLibrary`, and keep the Sprite or Vector switch in front of the lookup. Icons are plain registry frames too (`PowerUpSprites.of(kind)`): their entries use `fit: "trim"` (contain into the output, measure the visible art on that cut, contain it into the output minus `padding`), and kinds without sheet art are drawn from 16 x 16 pixel art (`presentation/power_up_pixel_art.dart`) and added with `SpriteRegistry.registerDrawn`; `PowerUpIcon` shows icons in widgets. Everything is drawn with nearest-neighbor scaling. Read `docs/SPRITES.md` before adding or fixing a sprite (sheet rules, manifest fields, `tool/sprites/make_atlas.py`, the isolation and golden tests). Held weapons follow each skill's grip (`SkillDefinition.weaponGripInset` forward/back, `weaponGripSide` sideways in ball radii, mirrored for the second hand, `weaponGripRotation` in degrees, mirrored when the sprite flips; built-ins default to 0 except the blade inset): `PowerUpPainter.heldCenter` / `heldSpriteAngle`, and `paintHands` follows both. Skill editor > Appearance > "Preview grip" opens `GripPreviewDialog` (real held-weapon painter, facing right and left, live sliders; Done writes back, Cancel discards). Field power-ups look like small balls (white, ringed in the power-up's color, pulsing). Until the images load, simple vector glyphs stand in. The scoreboard shows 10 hearts per ball in power-up modes (`HeartsRow`).
  - **Sounds:** the battle screen plays power-up sounds when `PowerUpSystem` counters rise.
- **Rim slots and lines** (`domain/fan_line.dart`, rules in the controller's class doc). The rim has `kRimSlotCount` (180) fixed slots, each free or owned by one ball, and the controller tracks ownership in `_slotOwners`. Each owned slot is a `FanLine` from its rim anchor to the owner's center, and `ball.fanLines` holds only the lines the ball currently owns. An opponent's *body* overlapping a line cuts it and frees the slot. A wall hit on a free slot claims the free run from the contact point to the ball's own nearest line. A ball with no lines is eliminated. These rules were worked out from the reference video; see `docs/reference_video_analysis.md` before changing them. Its notes also show that "beam mode", "two-blade fans" and "fan aimed at the opponent" from the older catalog aren't separate mechanics.
- **Ball look** (`BallLook`: Pictures or Faces, `pref:look`): Faces draws each arena ball as a smiley in its own color, and the VS header shows each ball's picture with a small live smiley at its lower right (overlapping a little, same base line; `_VersusHeader.smileyScale`). The smiley has white eyes whose pupils track the nearest opponent and an expression that worsens with lost life and winces on hits (`presentation/ball_face_expression.dart`). It is cosmetic, but replay links carry it (`look=faces|pictures`, `ReplayLink.look`) so a saved or shared replay and its video show the look the match was played with; older links without it use the viewer's own setting.
- **Hair and ball gender:** `BallHairPainter` draws `HairStyles.count` (45) code-drawn styles (paths and circles, no blur) on top of the body in every look; style `s` is family `s ~/ 5`, variant `s % 5`. Styles 0-14 (spikes, rounded cuts, swept/mohawk) are the male pool, 15-19 (the old long cut with a ponytail) and 20-44 (long straight, ponytail, two pigtails, bob, top bun) the female pool (`HairStyles.male` / `female`, `BallHairPainter.maleStyles` / `femaleStyles`). `CustomBall.gender` (`BallGender none|male|female`, picked in the ball editor, key `ball-gender`) is cosmetic: a none ball only gets hair with "Random hairstyles" (the shuffled style 0-19, as before); a male or female ball always gets hair from its pool: with random hairstyles the shuffled style shifted by the seed (`HairStyles.styleFor`), without it a pure hash of the ball id, and a palette color by the same hash. No RNG draws either way (the shuffle uses its own `math.Random(seed ^ ...)`). Custom balls carry it in links as `x` inside `c.` (male/female only; anything else rejects the link); group balls read it from `group_balls.gender`. `flutter test tool/hair/render_hair_test.dart --dart-define=OUT=<file.png>` renders a contact sheet of every style in both looks.
- **HP bars** (Match Setup > Appearance > "HP bars", Off by default, per match-type profile `match-<profile>-hp-bars`): a thin bar above each ball in play (`presentation/hp_bar.dart`, `hpBarFor` / `HpBar.paintAll`), drawn after all balls with plain rects and cached Paints. It fills by life of full life in Arsenal (gold past full, up to the match's `arenaMaxLife`) and by lines left of `startLines` in Threads and All-Out (told apart by `startLines > 0`); green above 50%, amber above 25%, red below. Cosmetic: `MatchConfig.showHpBars` -> `ArenaCanvas` / `ArenaPainter` and `ReplayStyle.showHpBars` (video), never in links; opened links use the viewer's own choice. The Power-up test always shows them. `flutter test tool/bench/paint_bench_test.dart --dart-define=HP_BARS=true` benches with them on.
- **Yes or No question:** with the decision pack, Match Setup shows "Your question". It replaces the headline in the battle screen and the video, and the winner card says "Answer: <winner>". It is cosmetic and travels as `q=` (`ReplayLink.cleanQuestion`, 100 characters at most) and in short links (`replays.question`, migration 010).
- `SimulationState` is a snapshot handed to the UI. It exposes the controller's **mutable** ball, particle and floating-text objects directly; nothing is copied.
- **Painting performance:** the arena uses no blur filters (`MaskFilter`). Glows are radial gradients or wide translucent strokes, and sparks are plain dots. Fan lines are drawn in one `drawRawPoints(PointMode.lines)` batch per ball, never as stroked paths. Cover images are filled through an `ImageShader`, not a clip. Text layouts (floating labels, initials) are cached. Keep it that way for low-end phones. `flutter test tool/bench/paint_bench_test.dart` gives before/after paint timings.
- Leftover code from the earlier designs: `TerritoryEngine` (360 rim sectors) and `thread.dart` are no longer used by the app (the per-frame territory rebuild was removed for performance). Only `territory_engine_test.dart` still uses `TerritoryEngine`.

### Determinism

All simulation randomness must come from the match's `SeededRandom` (`core/utils/seeded_random.dart`), which the controller creates from `seed` (by default the current time). Tests pass explicit seeds and check that the same seed produces the same state (`match_simulation_controller_test.dart`). Any new random behavior should use the controller's `_rng` instead of `math.Random()`, and only draw from it *inside simulation steps*, never per rendered frame. Then the outcome depends only on the step sequence, not on the frame rate. Replays depend on this: `controller.seed` exposes the seed actually used.

### Video export and replay links (replay_export)

`ReplayVideoExporter` re-runs a match from `(contestants, seed)` off-screen at 30 fps. It draws 720x1280 frames with `ReplayFramePainter` (9:16 layout like the reference, reusing `ArenaPainter`) and feeds RGBA frames to a `VideoExportBackend`. `createVideoExportBackend()` picks the backend per platform:
- **Android** (`AndroidVideoExport`): a method channel `ballwars/video_export` into `android/app/src/main/kotlin/.../ReplayVideoEncoder.kt`. It encodes with MediaCodec H.264 plus MediaMuxer, converts RGBA→YUV420 in Kotlin, and runs on a background thread in `MainActivity`. It saves to the gallery (Movies/BallWars) via MediaStore, which needs Android 10+.
- **Web** (`WebVideoExport`, via `dart:js_interop`): `web/video_export.js` (`window.ballwarsVideo`) encodes with WebCodecs and muxes with the vendored `web/vendor/mp4-muxer.js` (MIT, v5.2.2; upstream is deprecated in favor of Mediabunny), then downloads the MP4 or opens the share sheet. `web/index.html` loads both scripts.
- **Elsewhere** it returns null, which hides SAVE VIDEO.

`ReplayLink` builds and parses share links. Because links come from anywhere, `fromUri` rejects anything the app couldn't have made: other than 2–4 balls, a non-finite speed or one outside 0.25–4×, custom balls with out-of-range mass, speed or name, or oversized links. Format: `<app>?seed=..&speed=..&balls=p.<presetId>,c.<base64 json>`. These are plain query strings, so there's no `#` and no server routing to set up on GitHub Pages; legacy `#/replay?..` links still parse. The home screen opens a link found in `Uri.base` at startup. Presets are referenced by id from `LocalBallRepository.presets`, so keep those ids stable. Uploaded ball images don't travel in links. Sharing tries a short link first (`?r=<7-char code>`, stored in the Supabase `replays` table by `SupabaseShortLinkRepository`; migration 007 caps each account at 200 per day), because Messenger mangles the long ones. It falls back to the long link when there's no backend.

### Built-in ball packs (ball_packs)

`tool/build_packs.mjs` (run with `node tool/build_packs.mjs`) downloads brand logos and flags into `web/packs/<group>/<ball>.svg`. It also writes `web/packs/packs.json` (the catalog with brand colors) and `web/packs/LICENSES.md`. Sources, in order of preference: gilbarbara/logos (CC0, full-color), svgl, simple-icons (CC0, drawn in the brand color), and flag-icons (MIT) for countries. "Yes or No" is drawn in the script. "Ulam (Filipino food)" uses Wikimedia Commons photos, listed by exact file name; the script accepts only CC BY / CC BY-SA / CC0 / public-domain files and credits author, license and source in LICENSES.md. Photo balls are 384 px JPEGs that the painter center-crops into the ball. The packs deploy with the web app on GitHub Pages; Android reads them from `kWebAppUrl`. `BallPackRepository` loads the catalog, and pack balls get ids `pack:<group>/<ball>` and an `imageUrl`. `BallImageLoader` (core/utils) loads and caches ball images, drawing SVGs with flutter_svg. `BallFacePainter` draws logo balls (white ball, logo fitted inside) and cover/flag balls for both the arena and the video. `MatchColors` adjusts line colors per match so they're visible and distinct; the logos keep their real colors. `test/features/ball_packs/built_in_packs_test.dart` renders every pack SVG, so rerun it after rebuilding packs.

### User groups (custom_groups, Supabase)

`supabase/migrations/001_ball_groups.sql` creates the `ball_groups` / `group_balls` tables, the RLS policies and the `ball-images` bucket (public read, PNG/JPEG/WebP, 512 KB). Run it in the Supabase SQL editor and enable anonymous sign-ins. `main.dart` initializes Supabase with `SupabaseConfig` (the URL and publishable key are public by design). `SupabaseCustomGroupRepository` signs in anonymously on first use, so each device owns its groups. Group balls have ids `group:<uuid>` and appear in links as `g.<uuid>`. Run `002_admin_and_settings.sql`, `003_short_links_and_watermark.sql`, `004_saved_groups.sql`, `005_music_setting.sql`, `006_slow_motion_setting.sql`, `007_replay_limits_and_image_cleanup.sql`, `008_ball_size_and_pack_extras.sql`, `009_home_music.sql`, `010_replay_question.sql`, `011_power_up_tuning.sql` ... `020_replay_documents.sql`, `021_fix_replay_tuning_check.sql` and `022_ball_gender.sql` after it (021 fixes a pattern in 011 that Postgres rejected, which broke share links for matches with changed power-up numbers; `test/supabase/migrations_test.dart` guards against it). 022 adds `group_balls.gender`; run it in the Supabase SQL editor. Until it runs, `SupabaseCustomGroupRepository` reads and saves balls without the column: an `OptionalColumn` sends each query with `gender`, and on a missing-column error (42703 / PGRST204) retries without it and leaves it out from then on. Every group is readable by everyone. Any group can be shared as `<app>?g=<group uuid>` ("Copy share link" in My Groups); opening the link offers to add the group to the viewer's `saved_groups`. Match Setup has a **Mine | Default | Shared** filter above the category dropdown (it starts on Default and is remembered as `pref:category-filter`). It lists the built-in packs, the user's own groups (tag "Mine"), or the saved ones ("Shared"). The admin picks other players' groups with the "In my categories" switch in Everyone's groups. The admin can also add any group to a built-in category ("Add to main category…", `ball_groups.pack_id`, which a trigger lets only the admin set). Match Setup appends those `packExtras()` balls to that pack for everyone. `pack_id = 'own'` (`CustomGroup.ownCategory`, the dialog's "New category" option) makes the group a main category of its own under Default, with the category id `main:<group id>`. Everyone's groups is sorted A–Z and has a search box (group or ball names). Players can "Submit to main categories" (`submitted_at`), and submitted groups are listed first for the admin. Both columns come with migration 008 and are queried separately from the common group columns, so the app still works before it's run. `BallEditorSheet` adds and edits balls: `CircleCropper` lets the user drag and zoom the picture behind a fixed circle. `ImagePrep` decodes it at 1024 px at most (on web via decode-then-shrink, because the web engine's `ImageDescriptor` can't report sizes) and turns the chosen crop into a 256 px PNG before upload, and it also suggests a line color. `MyGroupsScreen` manages groups, and groups with balls show up as Match Setup categories (a searchable `DropdownMenu`). Tests use fake repositories; nothing in `test/` touches the live project.

On wide screens the battle screen splits in half: the game and winner card on the left, the scoreboard on the right. The home screen opens replay links found in `Uri.base`; it navigates with `await WidgetsBinding.instance.endOfFrame`, not `addPostFrameCallback`, because after awaiting packs or groups an idle screen schedules no new frame.
